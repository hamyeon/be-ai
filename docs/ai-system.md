# Vintic AI 시스템 기술 문서

크롤링부터 Vision 분석, 가격 계산, 추천, Purchase Agent까지 — AI 트랙의 전체 기술을 한 곳에 모은
살아있는 문서다. 새 측정이나 구조 변화가 생기면 여기에 추가한다.
다른 파트 팀원이 AI 쪽 진척도를 파악하는 문서이기도 하다 - 바로 아래 "지금 상태"만 봐도
무엇이 끝났고 무엇이 남았는지 알 수 있게 유지한다.
각 주제의 깊은 내용은 문서 지도(맨 아래)의 개별 문서에 있다.

**관통하는 원칙 하나**: 모든 숫자는 근거가 있어야 하고, 근거가 없으면 없다고
말한다. 측정하지 않은 값을 측정한 것처럼 내보내지 않는다.

**알려진 위험**

- `POST /api/products/analyze`는 2026-10-01부터 로그인이 필요하다(`JwtSecurityConfig` anonymous 목록에서 제거,
  다른 사용자의 분석 조회는 404). 호출마다 유료 Vision API(케이스당 약 $0.05, 실루엣·상태 Haiku 적용 후 약 $0.018)를 부르는데 사용자별 호출 제한은
  아직 없어, 로그인한 사용자는 제한 없이 비용을 쓸 수 있다.
- `POST /api/products/calculate-price`도 2026-10-07부터 로그인이 필요하다. 그전에는 익명으로 열려 있고 소유자 검증도 없어,
  순차 증가하는 `analysisId`로 남의 세션을 `COMPLETED`로 만들어 소유자의 가격 계산을 막을 수 있었다(다른 사용자의 세션은 404).
- OpenAI 크레딧이 소진된 상태다. Vision은 Claude로 옮겼지만 Goal 파서·Matcher·임베딩은 아직 OpenAI다.
  파서는 규칙 기반으로 대체되고(경고 부착), 임베딩 실패는 상품 등록을 막지 않는다. **Matcher는 대체 없이 실패 = 후보 제외**라
  Agent가 아무 경매에도 참여하지 못한다. 충전 전까지는 `PURCHASE_LISTING_MATCHER=rule`(실측 97%·거짓 양성 0)로 둔다.
- Vision 벤더 비교에서 GPT는 같은 빠른 설정으로 다시 재지 못했다(§3-4 감안할 점).

## 1. 데이터 수집 (크롤링)

### 1-1. 당근마켓 — 시세의 몸통

- **왜 당근인가**: 우리 서비스가 개인 간 중고 거래라, 예측해야 하는 가격은
  KREAM 검수 새제품가가 아니라 당근에서 손바뀜되는 가격에 가깝다.
  실측으로도 당근의 새상품(DS) 매물조차 KREAM 체결가의 70% 수준에 올라온다.
- **수집 방식**: robots.txt가 허용하는 검색 경로만, 요청 간격 1.5초.
  서울 22개 동(20대 밀집·패션 상권 위주) × 검색어 36개(브랜드 19 + 일반 8 +
  표본 얇은 모델 직접 검색 9).
- **누적 방식**: URL 기준 중복 제거 후 이어붙인다(적정 주기: 하루 1회 — 시간 단위
  재실행은 신규가 거의 없음을 실측).
- **현재 규모**: 46,146건(마지막 수집 2026-09-04). 이후 수집은 멈췄다(아래).

**2026-09-17부터 수집 0건.** 구성품 계수 표본을 늘리려고 재수집하다 발견했다.

- 검색 경로가 `/kr/buy-sell/?search=`에서 `/kr/search/buy-sell/?q=`로 바뀌었고, 새 페이지에는
  크롤러가 읽던 구조화 데이터(`ld+json`)와 가격이 HTML에 없다. 모든 지역에서 0건이다.
- robots.txt에 AI 에이전트·크롤러(ClaudeBot, GPTBot, Scrapy 등)를 사이트 전체에서 막는 그룹이 추가됐다.
- 고치려면 사이트가 명시적으로 막은 방식(내부 API·클라이언트 렌더링 긁기)으로 가야 해서 **우회하지 않았다.**
  9/4 데이터가 현재 최종본이고, 재개 여부는 팀 결정이 필요하다.
- 영향: 표본 부족으로 보류한 계수(C등급, 풀박스 - §4-2, §4-4)를 채우려면 수집량이 약 1.2~1.4배 필요한데
  그 경로가 막혔다. 9/10 커버리지 확대처럼 **이미 모은 원본을 다시 읽는** 방식은 계속 가능하다.

### 1-2. 후르츠패밀리 — 당근과 같은 종류의 가격

개인 간 중고 거래라 당근과 한 바구니에 합쳐 시세를 낸다. 특정 모델
(닥터마틴 1461, 헌터 레인부츠, XT-6)에서 비중이 크다.

### 1-3. KREAM — 시세의 잣대

- **역할 셋**: ① 상태 계수의 분모(새제품가 대비 감가율) ② 2순위 가격의 기준 시세
  ③ 색상 프리미엄(상품 = 컬러웨이 구조라 색상별 체결가가 원래 형태).
- **제약**: 소프트 차단(짧은 버스트 ~15요청만 허용, 이후 전부 500). 대응:
  요청 간격 10~20초, 연속 5회 실패 시 자동 중단, 우선순위 모델 검색어부터 소비.
  탐지 우회는 하지 않는다 — 차단되면 시간을 두고 다시 간다.
- **수집 단위**: 상품 정보 + 최근 체결 5건(사이즈/가격/시각). 참조로 쓸 상품은
  사람이 고른다(표준 컬러웨이만 — §2 참조 품질 분류).
- **현재 규모**: 우선순위 17개 키워드 수집 완료(9/7). 참조 26개 모델, 상태 계수 표본 1,884건.

### 1-4. eBay — 참고 정보로 강등 (측정으로 결정)

당근 실거래 예측 오차를 쟀더니 KREAM 단독 25% < 혼합(0.7/0.3) 38% < eBay 단독
155%. eBay는 해외 호가라 국내 실거래의 약 2.5배이고, 중고 매물 호가인데
새제품가처럼 상태계수를 곱하는 이중 감가 버그도 있었다. 기준 시세에서 빼고
응답에 참고로만 싣는다. (`secondary_price_eval.py`)

| 한글→모델 매핑 | `model_aliases.py`, `shoe_models.py` | "에어포스1"과 "Air Force 1 Low"는 문자로 안 겹친다. 숫자 별칭(530, 1461)은 브랜드 힌트가 함께 있어야 인정 — "530"만 잡으면 무관한 숫자가 붙는다. 긴 별칭부터 검사한다 — "조던1"이 "조던11"에 먹혀 조던11 매물이 조던1 시세로 새던 것을 #97에서 교정 |

`ModelAliasesTest`가 검사한다 — Vision 결과, Purchase Agent 파서, Matcher, 시세 조회가 전부 같은 키로 만난다.

## 3. Vision 분석 (사진 → 상품 정보)

### 3-1. 구조: 3단계 분리 호출

기본 `claude-sonnet-5`(effort low), **실루엣·상태 단계는 `claude-haiku-5-5`**(`vision.stage.{silhouette,condition}.model`, 2026-10-10).
라벨 단계(작은 글씨 판독, 최종 브랜드·모델명 우선)만 Sonnet 5다.
`vision.provider=openai`로 GPT 복귀 가능 — provider와 맞지 않는 단계 모델은 무시된다. 세 단계는 **동시에** 돈다
(`vision.stage.execution-mode=all-parallel`) — 전체 시간이 세 단계의 합이 아니라 가장 느린 한 단계 시간이 된다.

1. **실루엣**: 신발 종류, 브랜드, 모델, 색상
2. **라벨 판독**: 사이즈, 스타일 코드
3. **상태 판정**: 등급(DS/A/B/C/UNKNOWN), 하자 목록, 상태 설명, 박스 여부

세 단계 모두 분석용 768px 사본을 본다. GPT의 `detail`(low/high) 파라미터는 Claude에 없다.
동시 실행이라 2단계는 1단계 결과를 모른 채 라벨을 읽지만, 합칠 때 "라벨 값 우선, 없으면 1단계 값" 규칙이라
최종값은 같다.

환각 방지 장치: Structured Outputs(json_schema+strict), 근거(evidence) 없는
필드는 검증기가 null 처리, 공식 컬러웨이명은 라벨에 없으면 금지, 모르면
UNKNOWN/null(기권이 오답보다 낫다 — 기권은 사용자 확인으로 메워진다).

사용자 확인 여부(`needsUserConfirmation`)는 3단계 모델의 판단만 믿지 않는다. 동시 실행이라 3단계는 2단계가
사이즈를 못 읽은 걸 모르고 `false`를 낼 수 있어서(2026-10-07 프론트 실측), 브랜드·모델명·색상·사이즈 중 하나라도
비었거나 등급이 UNKNOWN이거나 경고가 하나라도 있으면 서버가 `true`로 켠다. `warnings`는 화면에 그대로
노출되는 사용자용 문구다("사이즈: 사이즈 라벨 보이지 않음" 형태 — 단계 번호·스키마 필드명은 붙이지 않는다).

### 3-4. 왜 Sonnet 5인가

교수님 피드백("분석 버퍼링이 불편하다")에서 시작했다. 사진 3장 기준 추천가까지 약 20초였고, 가격 계산은 ms 단위라
사실상 전부가 업로드 + Vision이었다. 조건은 **"벤더를 바꿔도 지금(GPT)보다 느려지면 안 된다"**였다.

| 후보 (사진 1장 18건) | 평균 시간 | 등급 오답 | 모델명 정답/오답 | 결과 |
| --- | --- | --- | --- | --- |
| GPT-4o (당시 운영) | 10.3초 | 0 | 3 / 2 | 기준 |
| Haiku 4.5 | 20.2초 | **3** | 4 / 6 | 탈락 — 등급 오답 |
| **Sonnet 5** | **9.0초** | 0 | 8 / 5 | **채택** — 속도 조건을 통과한 유일한 후보 |
| Opus 5 | 11.8초 (최대 22.7초) | 0 | 11 / 1 | 탈락 — 정확도는 최고지만 가끔 20초 초과 |

처음 Opus 5로 쟀을 때는 31초로 GPT의 3배였다. 원인은 사용량 한도나 이미지 전송이 아니라 **출력 토큰**이었다 —
같은 답인데 한국어 근거 문장이 Claude 토크나이저에서 잘게 쪼개져 GPT의 2.6배를 썼다. 근거를 영어 키워드로 줄인
v3 프롬프트로 가장 느린 단계의 출력이 738 → 350토큰이 됐다.

**감안할 점**

- OpenAI 크레딧이 소진돼 **GPT를 같은 빠른 설정(v3 + 동시 실행)으로 재지 못했다.** 속도 이득의 대부분은 v3와 동시 실행에서
  나온다. 이 표는 "Claude가 GPT보다 빠르다"가 아니라 "현재 운영(GPT 순차)보다 빨라진다"로 읽는다.
- 모델·해상도·프롬프트·실행 방식 네 가지를 한꺼번에 바꿨다. 어느 변경이 정확도를 바꿨는지는 분리되지 않는다.
- 표본이 18·14건이라 1건 차이는 차이로 보지 않는다. 모델명(3 → 8), 색상(6 → 9)처럼 큰 차이만 결론에 썼다.

상세(조건, 단계별 시간, 설정값)는 `ai-vision-agent.md` "벤더 비교 실측" 절.

## 4. 가격 계산

### 4-1. 전체 폴백 체인

```
요청: (브랜드, 모델, 색상, 등급, 구성품)

1순위: 중고 실거래 (당근+후르츠, 65개 모델·6,173건)
  ①-a (모델, 색상 계열) 버킷 있음 (83개, 표본 10건+)
       → 그 색 실거래 중앙값 기준
  ①-b 없으면: KREAM 색상 프리미엄 있음
       → 모델 중앙값 × (그 색의 KREAM 체결가 / 모델 평균)
  ①-c 없으면: 모델 전체 중앙값 기준
  공통: × 상태 비율(그 등급 계수 ÷ 전체 매물 계수) × 구성품 반영률(§4-4)
  권장 범위 = 실거래 IQR(25~75% 구간) — ±5% 같은 임의 폭이 아니라 실제 분포

2순위: 1순위 매칭이 없으면 KREAM 새제품가 × 상태 계수 × 구성품
       (eBay는 참고 표시만)

3순위: 그것도 없으면 "시세 정보 없음" + 요청 로깅
       (틀린 값보다 없음이 정직하다. 로그는 다음 커버리지 확대의 우선순위 근거)
```

어느 경로로 계산했는지, 계수가 실측인지 기본값인지, 표본이 몇 건인지 —
전부 `reason` 문구로 응답마다 공개한다. 같은 입력의 결과는 Redis에 60분 캐시한다(`ai-pricing-agent.md`).

### 4-2. 상태 계수 (실측, 2026-09-07 기준)

계수 = 당근 실거래 중앙값 ÷ KREAM 표준 컬러웨이 새제품가. 원본은
`condition_rates.csv`이고 재측정 때마다 갱신된다.

| 등급 | 계수 | 출처 |
| --- | --- | --- |
| DS(새상품) | 0.612 | 실측 387건 |
| S(거의 새것) | 0.404 | 실측 105건 — 기본값 0.70이 크게 후했음이 드러남 |
| A | 0.369 | 실측 628건 |
| B | 0.266 | 실측 300건 |
| C | 0.20 | 기본값 — 과포착 정제 후 실측 0.23(28건)으로 서열 정합, 표본 부족으로 채택 보류 |
| ALL(기준선) | 0.389 | 실측 1,884건 — 1순위 비율의 분모 |

- 분모가 ALL(전체 매물)인 이유: 시세 중앙값이 전체 매물에서 나온 값이라
  분자·분모의 모집단이 같아야 한다. UNKNOWN을 분모로 쓰면 새상품이 빠져
  전체가 일괄 높게 추천되는 편향이 생긴다(실측으로 확인 후 교정).
- 상태 미상(UNKNOWN) 요청은 비율 1.0 — 시장 중앙값 그대로.
- 모델별 계수가 있으면 우선(감가 속도가 모델마다 다르다 — 에어포스1 0.44 vs
  993 0.61. 통합 계수로 뭉개면 993이 31% 낮게 추천된다).
- C등급 경위: 정제 전에는 C가 0.32로 B(0.266)보다 높았다. "하자 없음" 같은 부정 표현과 "살짝" 같은 정도 표현까지
  C급 신호로 잡아 멀쩡한 매물이 섞였기 때문이다. 고치고 나니 서열은 맞았지만 28건만 남아 기준(50건)에 못 미친다.

### 4-3. 색상 반영 (#93)

- 색상별 가격차는 실재한다: 슈퍼스타 블랙 -39% vs 화이트 -5%, 덩크로우 블루 +112%.
- 색상 표기는 계열로 정규화해 비교한다(gray=grey=회색). 색상 버킷은 표본
  10건+일 때만 존재 — **색상 시세는 통계적으로 설 때만 쓰고, 정확도가
  나빠지는 경로는 없다.**
- 희소성(매물 수)은 반영하지 않는다: 점유율↔프리미엄 상관 +0.108(무상관).
  희소한 색에는 한정판과 비인기색이 섞여 매물 수로는 구분 불가(ADR 12).

### 4-4. 구성품 계수 (실측, 2026-09-16, #104)

"박스 없으면 5% 깎는다(0.95)"는 정한 값이지 잰 값이 아니었다. 당근 실거래로 쟀다. 원본은 `component_rates.csv`.

| 구성품 | 이전 | 현재 | 근거 |
| --- | --- | --- | --- |
| NONE(박스 없음) | 0.95 | **0.90** | 실측 1,214건. 기존 값은 실제 차이의 절반만 반영하고 있었다 |
| PARTIAL(일부) | 0.97 | **1.00** | 실측 993건 |
| FULL(풀박스) | 1.00 | 1.00 (기본값 유지) | 실측했지만 **미채택** — 셀마다 0.76~2.27로 흩어짐 |
| 미상 | 0.97 | 1.00 | 판매자가 안 적은 것과 "일부"는 다른 신호라 보정하지 않는다 |

- **판정률 개선**: 크롤링 때 매긴 박스 판정은 있음/없음 2진값에 판정률 10.7%였다. 저장된 설명을 다시 읽어
  FULL/PARTIAL/NONE 3분류로 바꾸니 판정률 20.2%. 재크롤링은 필요 없었다.
- **상태를 통제한다**: 박스 있는 매물은 45%가 새상품, 없는 매물은 19%다. 그냥 비교하면 박스 값이 아니라 상태 값을 잰다
  (통제 없이 재면 0.774). 같은 (브랜드 × 상태 등급) 셀 안에서만 비교한다.
- **상대 보정으로만 쓴다**: 박스를 설명에 적는 매물이 애초에 비싼 매물이라(설명 길이와 가격이 비례), 기준선을 전체 매물로
  잡으면 "박스 없는 매물이 26% 비싸다"는 엉뚱한 값이 나온다. 기준선은 그 셀에서 구성품이 판정된 매물이다.
- **재현성 검증**: 표본을 매물 URL 해시로 절반씩 갈라 따로 산출했다. NONE 0.868/0.915, PARTIAL 0.962/1.000으로 재현되고,
  FULL은 1.542/1.346으로 흔들려 미채택 판단과 일치한다.
- FULL을 재려면 판정 매물이 약 1.2~1.4배 필요하다 — 당근 수집 중단(§1-1)으로 막혀 있다. 결정 기록은 ADR 13.

### 4-5. 경매 상세 AI 추정가는 서버가 계산한다 (2026-09-10, #96)

- **문제**: 경매 상세의 `aiEstimatedPrice`는 `Product.recommendedPrice`를 그대로 보여줬다. 이 값은 판매자 앱이 추천가를 받아
  **다시 서버로 보낸 숫자**라 판매자가 부풀릴 수 있다. 구매자에게 보이는 "AI 시세"가 판매자 입력값이었던 셈이다.
- Purchase Agent는 입찰 상한을 `min(예산, AI 시세 × 비율)`로 잡으므로, 그 값을 믿으면 판매자가 구매자 Agent의
  입찰 상한을 끌어올릴 수 있는 경로가 된다.
- **해결**: `AuctionQueryService`가 조회 시점에 `PriceEstimateProvider`로 직접 계산한다. 새 계산식은 없다 — 기존 가격 계산을
  그대로 부르고 60분 캐시를 탄다. 시세가 없거나(카탈로그 밖 모델) 계산이 실패하면 null이고, 실패가 경매 상세 조회를
  실패시키지는 않는다.

### 5-3. 테스트

- 단위: 계수 조합 방식, 폴백 체인, 색상 정규화(단어 단위·긴 표기 우선),
  서열 유지, 근거 공개 — 값이 아니라 **성질**을 검증해 재측정에도 안 깨진다.
- E2E 21케이스: AI 트랙 14(색상 경로 포함) + 전 구간(등록→결제) 7.

### 5-4. 아직 못 잰 것 (다음 채점표)

- **최종 정확도**: "추천가대로 올리면 실제로 그 가격에 팔리는가"는 정답지(실제
  낙찰가)가 없어 못 쟀다. 서비스가 열리면 "추천가 대비 낙찰가"가 진짜 채점표다.
- 색상 미판독 매물 43%: Vision 사진 라벨링으로 채울 계획 — 제목 색상이 있는 절반으로
  라벨 신뢰도를 선검증한 뒤 쓴다.
- 당근 가격은 호가지 체결가가 아니다. IQR을 함께 내려 분포를 숨기지 않는다.
- Purchase Agent의 LLM 파서·Matcher 정확도(유료 호출이라 아직 안 돌림), 실사용자 문장 분포.
- Vision 평가 셋 크기(18·14건). 벤더를 또 바꾸거나 설정을 분리해 재려면 셋부터 키워야 한다.

## 6. Purchase Agent (구매자 Agent) (AI #95 + 백엔드 #109)

사용자가 "뉴발 990, A급 이상, 15만원 이하로 하나"라고 등록하면 시스템이 여러 경매를 대신 탐색·입찰하는 기능이다.
AI 트랙이 부품 세 개를 만들었고(9/10), 백엔드 워크플로(jchaeyun, 9/25 머지)가 셋을 모두 연결했다.

```
문장 ─ Goal 파서 ─► 초안 ─ 사용자 확인 ─► Goal 등록
                                             │
5분마다 (PurchaseGoalScanScheduler: 만료 → 결과 관찰 → 탐색·참여)
  pre-filter  모델 키(별칭 표)·최소 등급(GoalCondition)·사이즈 hard 조건·예산     ← PurchaseGoalCandidateFinder
  랭킹        Matcher 판정 + 서버 시세 대비 할인율 (판매자 추천가는 안 씀)       ← PurchaseGoalCandidateRanker
  참여        입찰 직전 서버 시세 재계산 → 상한 = min(예산, 시세 × 비율)        ← PurchaseGoalEngagementService
```

- 탐색 스케줄러는 **기본 꺼져 있다**(`PURCHASE_AGENT_SCAN_ENABLED`, 기본 false). 켜야 Agent가 움직인다.
- 시세 재계산은 DB 락 밖에서 한다 — 캐시·외부 의존 호출을 기다리는 동안 경매 row를 잡지 않기 위해서다.
- **Matcher 기본 provider가 OpenAI다**(`PURCHASE_LISTING_MATCHER`, 기본 openai). Matcher는 설계상 실패 시 대체 없이
  그 후보를 제외하므로, OpenAI 크레딧이 없으면 모든 후보가 제외돼 Agent가 아무 데도 참여하지 않는다.
  충전 전까지는 `rule`로 둔다 — 아래 실측상 규칙 기반이 거짓 양성 0이라 안전한 쪽이다.
  파서는 OpenAI가 실패하면 규칙 기반으로 대체되므로 동작은 한다(경고가 붙는다).

**원칙**: LLM은 해석만 하고 서버가 검증한다. LLM이 낸 값이 사람 확인 없이 입찰 상한이나 입찰 금액에 닿는 경로는 없다.

| 부품 | 하는 일 | 상태 / 수치 |
| --- | --- | --- |
| Goal 파서 (`POST /api/purchase-goals/parse`) | 문장 → 예산·모델 키·사이즈·최소 등급·자유 조건 초안 | 규칙 기반 + OpenAI(실패 시 규칙으로 대체). 규칙 기반 50/50 |
| 매물 Matcher | "이 경매 매물이 목표에 맞는가" 판정 | 규칙 기반 + OpenAI. 실제 당근 매물 59건에서 규칙 97%, **거짓 양성 0** |
| AI 시세 provider | Agent 입찰 직전 서버가 시세 재계산 | 기존 가격 계산 재사용. §4-5와 같은 이유로 판매자 값을 안 쓴다 |

- **파서 50/50은 믿을 수 있는 숫자가 아니다.** 테스트 문장과 규칙을 같은 사람이 만들었다. "만든 테스트는 다 처리한다"이지
  실사용 정확도가 아니다. OpenAI 파서·Matcher는 만들었지만 아직 측정하지 않았다.
- **Matcher는 실제 매물이라 더 믿을 만하다.** 처음 거짓 양성 4건 중 3건이 설명란 때문이었다 — 검색 노출용 브랜드 나열
  ("나이키 발렌시아가 슈프림 …"), 다른 모델과의 사이즈 비교. 그래서 규칙은 설명란을 믿지 않는다. 대신 놓치는 매물이
  2건 생겼는데, **잘못 사는 것보다 놓치는 쪽이 안전하다**(놓친 매물은 다음 탐색에 다른 후보가 있다).
- 검증기는 LLM 판정을 false 쪽으로만 뒤집는다(박스만 판매, 아동용, 여러 켤레, 브랜드 불일치, 다른 모델).
- 사이즈(`sizeKr`)는 설계안 계약에 없어서 AI 쪽에서 추가했고, 백엔드 pre-filter가 hard 조건으로 반영했다
  (Goal에 사이즈가 있으면 사이즈가 다르거나 없는 매물은 제외).

AI 부품 상세와 코드 지도는 `ai-purchase-agent.md`, 백엔드 쪽 계약 조사는 `purchase-agent/day0-contract.md`.

## 7. 추천 엔진 (요약)

- 상품 등록 시 text-embedding-3-small(1536차원)으로 벡터 생성. 실패해도 상품
  등록은 롤백되지 않는다(트랜잭션 분리 — troubleshooting 2번의 교훈).
- 개인화: 행동 로그 가중(입찰 3.0/찜 2.0/조회 1.0/체류 1.0)으로 취향 벡터를
  만들어 코사인 유사도 정렬. 행동 3건 미만은 Cold Start Fallback(마감임박+인기).
- 벡터 없는 상품도 버리지 않고 뒤에 붙인다(similarity는 정직하게 null).
- Fallback은 Redis 60초 캐시 + 입찰/경매 종료 시 즉시 무효화.

## 8. 관측성 (요약)

- 모든 AI 호출(OpenAI·Claude, Vision·파서·Matcher·임베딩)을 DB에 기록(모델명/프롬프트 버전/응답/토큰/지연/실패 유형),
  보존 기간 후 자동 정리. Micrometer 지표(ai.calls/latency/tokens)에 무한 카디널리티 태그 금지 원칙.
- 분석 큐 지표: Redis 오류 횟수, 회수(재시도) 건수 — 회수가 급증하면 Vision 호출 실패율이 오른 신호다(`ai-async-analysis.md`).
- 시세를 못 준 요청(브랜드·모델)을 로깅 — 커버리지 확대 우선순위를 감이 아니라
  실요청 빈도로 정한다.
