# 아키텍처 결정 기록 (ADR)

AI·조회·비동기 트랙에서 내린 설계 결정과 그 근거를 남긴다.

기존 문서(`ai-infra-design.md`, `vision-agent.md`, `pricing-agent.md` 등)에 이미 정리된
결정은 여기서 되풀이하지 않고 참조만 건다. **코드 주석과 커밋 메시지에만 흩어져 있던
결정**을 모으는 것이 이 문서의 목적이다.

파일을 나누지 않고 한 문서에 모은 이유는 결정 수가 열 개 남짓이고 서로를 참조하는
경우가 많아서다. 개수가 늘면 `docs/adr/`로 쪼갠다.

## 1. 상품 벡터를 MySQL에 저장한다

**맥락**

추천에 쓸 상품 임베딩(1536차원)을 어디에 둘지 정해야 했다. Week 2 PoC에서는
`InMemoryEmbeddingStore`를 썼는데, 애플리케이션을 재시작하면 전부 사라진다.

**결정**

MySQL에 `LONGBLOB`으로 저장한다. 유사도 계산은 애플리케이션에서 한다.

**근거**

- 기동할 때마다 임베딩 API를 다시 부르면 비용과 기동 시간이 상품 수에 비례해 늘어난다
- Redis Vector 도입은 `ai-infra-design.md` §2에서 이미 보류로 결정했다
- 지금 상품 수에서는 메모리에 올려 코사인 유사도를 계산하는 편이 충분히 빠르다

**결과**

정석은 아니다(전용 Vector DB 대비 검색이 비효율적). 규모가 커지면 재검토해야 한다.

`float[]`를 바이트로 직렬화해 넣는다. JSON 문자열로 넣으면 20KB가 넘고 파싱 비용도 든다.
대신 사람이 읽을 수 없어서, 어떤 텍스트로 만든 벡터인지 `sourceText`를 같이 남긴다.
임베딩 입력을 바꿨을 때 재생성 대상을 가려내려면 필요하다.

> **주의**: `@Lob`만 붙이면 MySQL에서 `TINYBLOB`(255바이트)으로 생성돼 6,144바이트 벡터가
> 저장되지 않는다. `columnDefinition = "LONGBLOB"`을 명시해야 한다.
> 자세한 경위는 `troubleshooting.md` 1번.

## 2. 추천 벡터를 기동 시가 아니라 요청마다 읽는다

**맥락**

이슈에는 "`ProductVector` 영속화 + **기동 시 로드**"로 적었다. 구현할 때 메모리를 아끼고
벡터 갱신이 즉시 반영된다는 이유로 요청마다 `findAllById`로 읽는 방식으로 바꿨다.

**결정**

요청마다 읽는 방식을 유지한다. 단, 한계를 측정해 코드에 숫자로 남긴다.

**근거**

측정 결과 이 선택에는 실제 비용이 있었다. Fallback 경로(벡터를 쓰지 않는 순수 DB 쿼리)
대비 추가 시간을 각 50회 측정했다(p50).

| 경매 수 | Fallback | 개인화 | 추가 |
| --- | --- | --- | --- |
| 100 | 33ms | 46ms | +13ms |
| 1,000 | 33ms | 131ms | +98ms |
| 3,000 | 29ms | 317ms | +288ms |

병목은 유사도 계산이 아니라 **벡터 BLOB 전송**이었다. 벡터 하나가 6KB라 3,000건이면
요청마다 17.6MB를 읽는다. 유사도 계산 자체는 JVM에서 수 ms다.

**즉 이 지점에서는 원래 이슈에 적었던 "기동 시 로드"가 옳았다.**

**결과**

데모 규모(경매 수백 건)에서는 +13ms라 영향이 없어 지금은 유지한다. 캐싱은 "경매 목록 API +
Redis 캐싱" 작업에서 함께 다루는 편이 자연스럽다. 수치는 `RecommendationService`에 주석으로
남겨, 나중에 판단할 때 다시 재지 않아도 되게 했다.

**배운 것**: 설계를 바꿀 때 이유가 그럴듯하면 검증을 건너뛰기 쉽다. 그리고 개발 데이터가
4건이면 어떤 성능 문제도 보이지 않는다.

## 3. 부가 기능의 실패가 본래 기능을 실패시키지 않게 한다

**맥락**

추천용 벡터 생성, 행동 로그, AI 호출 기록은 모두 본래 기능에 얹은 부가 작업이다.
이것들이 실패했다고 상품 등록이나 경매 조회가 실패해서는 안 된다.

**결정**

쓰기를 별도 빈으로 분리하고, 그 빈에만 `@Transactional(REQUIRES_NEW)`을 건다.
호출하는 쪽은 트랜잭션 없이 `try-catch (Throwable)`로 감싼다.

```java
@Component
class XxxWriter {
    @Transactional(propagation = REQUIRES_NEW)
    public void write(...) { repository.saveAndFlush(...); }   // 프록시 경계
}

@Service
class XxxService {
    public void record(...) {
        try { writer.write(...); }
        catch (Throwable e) { log.warn(...); }                  // 커밋 실패까지 잡힌다
    }
}
```

**근거**

단순히 `@Transactional` 메서드 안에서 `try-catch`를 하면 **동작하지 않는다.** 두 가지 이유다.

1. `save()`의 INSERT는 트랜잭션 커밋 시점에 실행된다. 즉 메서드가 반환된 **뒤**라
   `catch`를 그냥 지나간다 → `saveAndFlush`로 실패 시점을 앞으로 당겨야 한다
2. `@Transactional`은 프록시로 동작하고 **커밋은 프록시가 메서드 반환 뒤에** 실행한다.
   그래서 커밋 자체의 실패는 여전히 `catch` 바깥이다 → 클래스를 나눠 프록시 경계를
   `try` 안쪽으로 옮겨야 한다

**같은 문제를 세 번 만났다.** `#49` 상품 벡터, `#51` AI 호출 로그, 그리고 찜 로그를 붙이며
`ActivityLogService`에서. 처음 두 번은 1번만 고치고 구조는 그대로 뒀는데, 두 번째에
테스트를 짜다 2번을 발견했다.

**결과**

`ProductVectorService`, `AiCallLogWriter`, `UserActivityLogWriter`가 이 형태를 따른다.
"예외를 던지지 않는다"는 계약은 **그 계약을 검증하는 테스트가 있을 때만** 지켜진다.
자세한 경위는 `troubleshooting.md` 2번.

## 4. 찜을 이벤트가 아니라 상태로 다룬다

**맥락**

찜(`LIKE`)은 추천 가중치 2.0으로 조회(1.0)보다 강한 신호다. 행동 로그는 원래
append-only 이벤트 기록인데, 찜은 해제할 수 있다.

**결정**

- `POST /likes` → 기존 `LIKE` 기록을 지우고 다시 남긴다
- `DELETE /likes` → `LIKE` 기록을 지운다

**근거**

- 해제했는데 로그가 남아 있으면 취향 벡터가 계속 가중치 2.0을 얹어, 사용자가 이미
  관심을 거둔 상품 쪽으로 추천이 기운다
- 찜 API는 멱등이라 이미 찜한 상품을 다시 눌러도 성공한다. 그때마다 로그를 쌓으면
  그 상품만 가중치를 계속 얻는다

**고려한 대안**

`auction_likes` 테이블(현재 상태의 원천)을 유저 벡터가 직접 읽는 방법도 있다. 상태가 항상
정확하다는 장점이 있지만, 행동 종류마다 읽는 곳이 달라져 `UserVectorService`가 복잡해진다.
가중치 계산을 한 곳에 모아두는 편이 낫다고 봤다.

**결과**

행동 로그가 완전한 append-only는 아니게 됐다. `LIKE`만 예외다.

## 5. 임베딩 입력에서 판매자 설명을 제외한다

**맥락**

상품 벡터를 만들 때 어떤 텍스트를 임베딩할지 정해야 했다.

**결정**

구조화된 필드(브랜드·모델·색상·사이즈·상태·가격대)만 쓴다. 판매자가 쓴 설명은 넣지 않는다.

**근거**

"네고 사절", "인스타 상점 ○○에서 파는 제품입니다" 같은 문구는 상품의 취향 특성과 무관하다.
이런 노이즈가 벡터에 섞이면 "네고 사절"이라고 쓴 판매자들의 상품이 서로 비슷해진다.

상태 등급은 `"A"` 대신 `"상태 좋은 중고"`처럼 자연어로 바꿔 넣는다. 임베딩 모델은
`A`라는 한 글자에서 의미를 얻지 못한다. 가격은 10만원 단위 구간으로 뭉갠다 —
1,000원 차이가 벡터를 흔들면 안 된다.

**결과**

검증: 나이키만 조회한 유저와 아디다스만 조회한 유저에게 같은 목록이 정반대로 정렬됐다
(0.977/0.906 vs 0.797/0.782). 브랜드를 별도 피처로 넣지 않았는데 임베딩만으로 갈렸다.

## 6. 개인화 전환 기준을 행동 3건으로 둔다

**맥락**

행동이 거의 없는 유저에게 개인화를 하면 한두 번의 우연한 클릭이 추천 전체를 지배한다.
어느 시점부터 개인화할지 정해야 했다.

**결정**

행동 로그 3건 이상이면 개인화, 미만이면 Cold Start Fallback. Fallback은 마감 임박과
인기 경매를 **번갈아 섞는다.**

응답에 `personalized`와 `reason`을 담아 **Fallback이라는 사실을 숨기지 않는다.**

**근거**

- 한쪽만 쓰면 목록이 편향된다. 마감 임박만 쓰면 인기 없는 경매가 올라오고,
  인기만 쓰면 이미 끝나가는 좋은 매물을 놓친다
- 프론트가 "회원님을 위한 추천"과 "지금 인기 있는 경매"를 다르게 쓸 수 있어야 한다.
  Fallback을 개인화처럼 보여주면 사용자가 추천 품질을 오해한다

가중치는 `BID 3.0 / LIKE 2.0 / VIEW 1.0`이다. 돈이 걸린 행동이 취향을 가장 강하게
드러낸다는 판단이고, 데이터가 쌓이면 조정할 값이다. 시간 감쇠는 넣지 않았다.

**결과**

3이라는 숫자에 실측 근거는 없다. 로그가 쌓이면 "몇 건부터 개인화가 Fallback보다 나은가"를
측정해 조정해야 한다.

## 7. AI 호출 기록의 단위를 세션이 아니라 호출로 한다

**맥락**

`promptVersion`, `modelName`, `latencyMs`, 토큰 사용량은 이미 전부 잡혀 있었지만
`log.info`로만 나가고 재시작하면 사라졌다.

**결정**

`AiCallLog` 테이블에 **API 호출 하나당 한 행**을 남긴다. `analysisId`로 세션에 묶는다.

**근거**

Vision 분석 한 건은 3단계로 API를 세 번 부르는데, `ProductAnalysisSession`에는 최종 결과
하나만 남는다. 어느 단계가 느렸는지, 어느 단계에서 스키마를 어겼는지 구분할 수 없었다.

실측으로 이런 표가 나온다.

| stage | latency | 토큰 |
| --- | --- | --- |
| silhouette | 4,440ms | 1,211 |
| label | 4,046ms | 2,170 |
| condition | 2,678ms | 2,501 |

**요청은 전문이 아니라 필요한 필드만 골라 담는다.** `HttpEntity`를 통째로 직렬화하는 습관을
들이면 언젠가 `Authorization` 헤더의 API 키가 DB에 저장된다. 시스템 프롬프트 본문도 뺐다 —
매 호출 같은 값이 수 KB씩 반복될 뿐이고 `promptVersion`으로 되짚을 수 있다.

**결과**

응답 본문을 통째로 담아 행이 크다. 기본 30일 보관하고 새벽 배치로 정리한다.
기록 1건 INSERT는 14.75ms로, Vision 단계 응답시간(2.7~4.4초)의 0.5% 수준이다.

같은 데이터를 Micrometer 지표로도 올린다. 용도가 다르기 때문이다 — 테이블은 "저 분석이
왜 저렇게 나왔는지" 한 건을 되짚는 용도라 응답 본문까지 담고, 지표는 "지금 실패율이
튀는지"를 훑는 용도라 숫자만 있으면 된다. 후자를 SQL로 하면 매번 수십만 행을 집계해야 한다.

## 8. 희소성을 가격에 반영하지 않는다

**맥락**

Week 5 항목에 "상태/구성품/**희소성** 보정"이 있었다. 매물 수를 희소성 지표로 쓰려 했다.

**결정**

반영하지 않는다. 산출은 해두되 가격 계산에는 넣지 않는다.

**근거**

매물 수는 **"희소해서 비싸다"와 "인기가 없어서 안 팔린다"를 한 숫자에 섞는다.**
부호가 반대인 두 신호라 그대로 곱하면 서로 상쇄되거나 엉뚱한 방향으로 움직인다.

제대로 하려면 체결 속도(등록 후 팔리기까지 걸린 시간)가 필요한데, KREAM 체결 이력 수집이
소프트 차단으로 막혀 있다(`troubleshooting.md` 4번).

자세한 산출 결과는 `pricing-agent.md` §2.

## 9. 상태 보정 계수를 실측으로 대체하되 표본이 부족하면 두지 않는다

**맥락**

추천가는 `(KREAM×0.7 + eBay×0.3) × 상태계수 × 구성품계수`로 계산한다. 상태계수
(`DS 0.80 / S 0.70 / A 0.60 / B 0.40 / C 0.20`)가 어디서 나온 숫자인지 설명할 수 없었다.

**결정**

당근 실거래 22,543건과 KREAM 참조를 대조해 실측한다. **표본이 충분한 등급·모델만** 바꾸고
나머지는 기존 값을 유지한다. 응답에 어떤 근거로 나온 값인지 밝힌다.

| 대상 | 기준 |
| --- | --- |
| 전 모델 공통 계수 | 50건 이상 |
| 모델별 계수 | 10건 이상 |

**근거**

측정해보니 기존 값이 실제로 틀렸다. 가장 흔한 "상태 미상"이 0.60인데 실측은 0.41이었다.
추천가가 31% 낮아진다.

**계수를 모델별로 나눈 이유**는 감가 속도가 다르기 때문이다. 상시 대량 생산되는 모델은
중고가 흔해 정가의 0.39지만, 물량이 적고 수요가 유지되는 모델은 0.60이다. 통합 계수
하나로 뭉개면 후자가 31% 낮게 추천된다. **993은 기존 기본값 0.60이 오히려 더 정확했다** —
통합 계수를 밀어붙였으면 개선이 아니라 개악이 될 뻔했다.

**표본 기준을 둔 이유**는 S등급이 12건뿐이었기 때문이다. 그 숫자로 0.70을 0.55로 바꾸면
근거 없는 계수를 근거 없는 계수로 바꾸는 것뿐이다.

**산출 방법에서 주의한 것**

비율을 낼 때 분자와 분모가 같은 물건이어야 한다. 처음에는 그렇지 않아 두 번 틀렸다.

1. **사이즈** — Samba OG 비율이 0.95로 나왔다. KREAM 참조가 전부 아동화(190~210)라
   성인 중고가를 아동 정가로 나눈 값이었다
2. **컬러웨이** — Air Max 95가 0.14로 나왔다. 참조가 전부 Neon(OG 프리미엄, 282,000원)인데
   당근 매물은 일반 컬러(중앙값 40,000원)였다. 전수 확인하니 참조 13개 모델 중 8개가
   한정/프리미엄 컬러였다

그래서 참조 품질을 수동 분류하고(`crawler/calibration/reference_quality.py`) 표준 컬러웨이인
모델만 쓴다. 협업·묶음판매·아동용 매물도 걸러낸다.

**결과**

실측 계수가 잡힌 건 4개 모델뿐이다. 나머지는 공통값으로 떨어지고, 그 공통값도
에어포스1 편중이 남아 있다. 다만 어떤 근거인지 응답에 드러나 사용자가 판단할 수 있다.

당근 가격은 **호가이지 체결가가 아니다.** 실제 거래는 그보다 낮을 수 있고 안 팔린 매물도
섞여 있다. 이 한계는 KREAM 체결 이력 수집이 풀려야 해소된다.

## 10. 관리 엔드포인트를 별도 포트로 분리한다

**맥락**

Actuator를 적용하면서 배포 서버에 `/actuator/*`가 인증 없이 열렸다. `metrics`에는
AI 호출 수·실패율·토큰 사용량이 담긴다.

**결정**

서비스는 8080, 관리는 8081로 나눈다. 보안그룹에서 8081 인바운드를 막는다.
노출 범위는 환경변수(`MANAGEMENT_ENDPOINTS`)로 뺀다.

**근거**

- 앱 앞에 리버스 프록시가 없어 **경로 단위로 접근을 막을 지점이 없다.**
  포트를 나누면 네트워크 레벨에서 가를 수 있고 애플리케이션 코드는 건드리지 않는다
- Spring Security는 지금 인증이 Mock 단계라, 실제 인증이 들어올 때 함께 하는 게 맞다
- 배포 서버에서 무엇을 열지는 배포를 맡은 쪽이 정해야 한다. 코드에 박아두면 노출 범위를
  바꾸는 데 재배포가 필요하다

`env`·`configprops`·`beans`·`heapdump`는 노출 목록에서 뺀다. 환경변수와 설정값을 그대로
반환해 API 키가 읽힌다. `MANAGEMENT_ENDPOINTS`에 `*`를 넣으면 이 넷이 전부 열리므로
**`*`는 쓰지 않는다.**

**결과**

**보안그룹에서 8081을 막지 않으면 이 분리는 아무 의미가 없다.** 포트만 나뉘고 둘 다
외부에 열린 상태가 된다. 배포 절차는 `deployment-config.md`.

지표를 보려면 EC2에 들어가거나 SSH 터널이 필요해져, 실제로 아무도 안 보게 될 위험이 있다.
그래서 확인 방법을 문서에 남겼다.

## 11. 지표 수집기(Prometheus)를 도입하지 않는다

**맥락**

`/actuator/metrics`는 **현재 값만** 보여준다. "어제보다 실패율이 올랐나", "프롬프트를
v3로 바꾼 뒤 응답시간이 어떻게 됐나"에는 답할 수 없다.

**결정**

보류한다. Micrometer로 지표는 남기되 수집 서버는 세우지 않는다.

**근거**

- Prometheus/Grafana는 수집 서버 운영이 따라붙는데, 같은 EC2에 올리면 리소스를 나눠 쓴다
- 같은 데이터가 `ai_call_logs`에 보관 기간만큼 쌓여 SQL로 집계할 수 있다.
  `idx_ai_call_prompt_version` 인덱스도 그 질의를 위해 걸어뒀다
- 수집기를 세울지는 배포 구성을 아는 쪽이 판단할 문제다

**결과**

추세를 보려면 SQL을 직접 써야 한다. 예시 질의는 `deployment-config.md`에 남겼다.
"추세를 봐야 하는 상황"이 실제로 생기면 그때 도입한다.
