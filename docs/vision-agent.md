# Vision Agent + 평가 하네스 (#21)

Vision 분석을 "한 번에 다 물어보고 나온 JSON을 믿는" 구조에서,
단계별로 물어보고 근거를 요구하고 결과를 측정 가능한 구조로 바꾸는 작업.

## 왜

지금(`product-analysis-system-v1.md`) 구조의 한계는 세 가지다.

1. **측정이 없다.** 프롬프트를 고쳐도 좋아졌는지 나빠졌는지 판단할 근거가 없다.
   EC2에서 몇 건 돌려보고 "brand/modelName/color/conditionGrade는 잘 나오는데 size는 안 나온다"는
   인상만 있는 상태다.
2. **근거가 없다.** 모델이 왜 그렇게 판단했는지 응답에 남지 않는다. 그래서 희소성("희귀 모델입니다")이나
   연식("20년 전 제품") 같은 확인 불가능한 설명이 섞여 들어와도 걸러낼 방법이 없다.
3. **한 번에 다 묻는다.** 실루엣 추정 / 라벨 판독 / 컨디션 판정은 필요한 이미지 해상도도, 실패했을 때
   대처법도 다른데 한 프롬프트에 뭉쳐 있다.

그래서 **측정 도구(하네스)를 먼저 만들고, 그다음 프롬프트/스키마를 바꾼다.**
순서를 뒤집으면 개선인지 아닌지 증명할 수 없다.

## 무엇을 잘해야 하는가 — size가 아니라 conditionGrade다

작업 초반에 "size를 못 채운다"를 핵심 문제로 잡았는데, 실제 흐름을 보면 그렇지 않다.

```
POST /analyze   이미지만 업로드 (사이즈 입력 없음)
      ↓
Vision 분석 → AWAITING_USER_CONFIRMATION
      ↓
POST /price     사용자가 brand·modelName·color·size·conditionGrade를 확정해서 보냄
```

`CalculatePriceRequest.size`는 `@NotNull` 필수이고, 가격 계산은 사용자가 보낸 값만 쓴다.
**Vision이 읽은 사이즈는 가격에 직접 쓰이지 않는다** — 사용자가 채울 폼의 초안일 뿐이다.

크롤링 데이터도 마찬가지다. 사이즈가 이미 텍스트로 있다(당근은 판매글 본문, 후르츠패밀리는 `size`
구조화 필드). 애초에 프로덕션에서 Vision이 크롤링 이미지를 보는 일은 없다 — 이 문서에 나오는 크롤링
이미지는 전부 평가용 샘플이다.

| 필드 | 사용자가 아는가 | Vision의 가치 |
|---|---|---|
| `size` | 본인이 앎 (라벨 보면 된다) | 낮음 — 타이핑을 줄여주는 정도 |
| `brand` / `modelName` | 대체로 앎 | 중간 — 시세 조회 키라 정확해야 한다 |
| **`conditionGrade` / `defects`** | **객관적으로 판단 못 함** | **높음** |

판매자는 자기 신발을 대체로 "A급"이라고 한다. 부풀릴 동기가 있고 스스로 객관적으로 매기기도 어렵다.
**사진 근거로 등급을 매기는 것**이 Vision이 사람보다 나은 지점이고, 가격에 직접 영향을 준다.

근거 강제(evidence)의 실질적 대상도 사이즈가 아니라 컨디션 등급이다. 사이즈는 틀리면 사용자가
알아채고 고치지만, "B등급"이라고 제시하면 사용자는 검증할 방법이 없어 그대로 확인을 누른다.

> 판매 상품의 사이즈를 정확히 알아내는 건 후순위 작업으로 둔다.

## 진행 순서

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 평가 하네스 + 정답 라벨 픽스처, 현재 v1 프롬프트 기준선 측정 | 구현 완료 (기준선 측정 대기) |
| 2 | 응답 JSON Schema 고정 (Structured Outputs) + 근거 필드 필수화 | 구현 완료 |
| 3 | 3단계 프롬프트(전체 형태 → 라벨/로고 → 오염/마모)로 분리, 환각 차단 규칙 | 구현 완료 |
| 4 | `detail: high` / 이미지 해상도 A/B를 하네스로 돌려 단계별 옵션 확정 | 측정 대기 |

## 1단계: 평가 하네스

### 평가 셋

`backend/src/test/resources/vision/harness-fixtures.json` — 당근마켓 크롤링 매물 18건.

정답(ground truth)은 **판매자가 본문에 적어둔 값**을 라벨로 썼다.
사이즈는 `사이즈 260`, 박스는 `박스 없어요` / `박스도 같이 드려요`, 상태는 `실착 1회` / `사용감많습니다`
같은 문장에서 뽑았고, 근거 문장은 각 케이스의 `groundTruthSource`에 남겨뒀다.

브랜드 18건은 Nike / Adidas / New Balance / Dr. Martens / Vans / Asics / Puma / Onitsuka Tiger /
Hoka / Converse로 분산시켰다. 한 브랜드에 몰리면 그 브랜드에만 맞는 프롬프트를 만들게 된다.

라벨이 애매한 매물(`사이즈 245~250`, `M5, W7 (240)`처럼 범위로 적힌 것)은 채점이 불가능해서 제외했다.

### 채점 기준

핵심은 **"못 채운 것"과 "틀리게 채운 것"을 절대 같이 세지 않는 것**이다.

| 결과 | 의미 |
|---|---|
| `CORRECT` | 값을 채웠고 정답 |
| `NEAR` | 한 등급 차이 (conditionGrade 전용) |
| `WRONG` | 값을 채웠는데 오답 = **환각** |
| `ABSTAINED` | null 또는 UNKNOWN, 모르겠다고 기권 |
| `NOT_LABELED` | 픽스처에 정답이 없어 채점 제외 |

여기서 나오는 지표는 세 가지다.

- **응답률(fill rate)** = 값을 채운 비율
- **응답 정확도(precision)** = 채운 것 중 맞은 비율 → 낮으면 환각이 많다는 뜻
- **전체 정확도(accuracy)** = 채점 대상 전체 중 맞은 비율

`size` 응답률을 올리는 게 이번 이슈의 목표지만, **응답 정확도를 떨어뜨리면서 응답률만 올리는 변경은
개선이 아니다.** 없는 사이즈를 지어내느니 기권하고 사용자에게 확인받는 쪽이 낫다. 표를 두 열로 나눠
보는 이유가 이것이다.

브랜드와 모델명은 표기가 흔들려서 완전 일치로 채점할 수 없다.
- 브랜드: 허용 표기를 배열로 두고(조던 → `["Nike", "Jordan"]`) 정규화 후 포함 관계면 정답
- 모델명: 식별에 필요한 키워드가 전부 들어있으면 정답 (`["chuck", "70"]` → "Chuck Taylor All Star 70 Hi" 정답)

### 이미지 해상도가 변수라는 점

크롤러가 저장해 둔 이미지 URL에는 `?q=82&s=300x300&t=crop`이 붙어 있다.
**그대로 쓰면 300x300 썸네일(약 17KB)이 내려온다.** 쿼리를 떼면 원본(약 280KB)이다.

이건 4단계(`detail: high`)와 직결된다. 300x300 이미지에 `detail: high`를 켜봐야 얻을 게 없으므로,
해상도와 detail은 반드시 같이 놓고 비교해야 한다. 그래서 픽스처에는 쿼리 없는 원본 URL만 담고,
`VisionHarnessImageVariant`가 실행 시점에 변형을 붙인다.

> 참고: 실제 서비스 경로(사용자 업로드 → S3)는 이 CDN 리사이즈 문제와 무관하다.
> 다만 크롤링 데이터를 학습/평가에 쓸 때는 계속 걸리는 문제라 백필 스크립트 쪽도 한 번 봐야 한다.

### 구성

```
src/test/java/com/vintic/backend/ai/vision/harness/
  VisionHarnessCase.java          픽스처 1건 (이미지 + 정답 라벨)
  VisionHarnessFixtures.java      픽스처 로더
  VisionHarnessImageVariant.java  해상도 변형 (ORIGIN / THUMBNAIL_300)
  VisionHarnessScorer.java        채점 (순수 함수)
  VisionHarnessReport.java        집계 + 표 출력
  VisionHarnessScorerTest.java    채점 로직 단위 테스트 (CI에서 항상 실행)
  VisionHarnessFixturesTest.java  픽스처 무결성 테스트 (CI에서 항상 실행)
  VisionPromptHarnessTest.java    실제 API 호출 (OPENAI_API_KEY 있을 때만 실행)
```

채점 로직을 API 호출과 분리해 둬서, 키 없는 환경에서도 채점 규칙 자체는 계속 검증된다.

### 실행

```bash
export OPENAI_API_KEY=...
./gradlew test --tests '*VisionPromptHarnessTest' \
  -Dvision.harness.variants=ORIGIN,THUMBNAIL_300
```

결과는 콘솔과 `backend/build/vision-harness/v1-{variant}.txt`에 남는다.
프롬프트를 바꿀 때마다 돌려서 이 표를 비교한다.

### 측정 결과 (2026-08-06, gpt-4o, 18건)

| | v1-ORIGIN | v1-THUMB300 | **v2-ORIGIN** |
|---|---|---|---|
| 호출/케이스 | 1.0 | 1.0 | **3.0** |
| 토큰/케이스 | 1,360 | 859 | **5,859** |
| 지연/케이스 | 3.2s | 2.4s | **9.3s** |
| BRAND 응답률/정확도 | 89% / 100% | 89% / 94% | 89% / 100% |
| MODEL 응답률/정확도 | 50% / 67% | 39% / 71% | 28% / 80% |
| SIZE 응답률 | 0% | 0% | 0% |
| GRADE 응답률/정확도 | 100% / 47% | 87% / 31% | 87% / 62% |

v2-THUMB300은 429(분당 토큰 한도)로 5건이 실패해 수치가 무효다. 재시도를 넣었으니 다시 측정해야 한다.

#### 세운 가설이 틀렸다: size 환각은 원래 없었다

"v1은 라벨이 안 보여도 사이즈를 채울 것이고 그건 환각"이라고 예상했는데, **v1도 18건 전부 기권했다.**
v1 프롬프트의 `Do not guess uncertain information`이 사이즈에는 이미 잘 먹고 있었다.

따라서 **근거 강제(`observedText` 요구)의 효과는 이 평가 셋으로 증명되지 않는다.**
평가 셋의 이미지가 전부 신발 전체를 찍은 대표 사진 1장뿐이라(당근 크롤링 3,337건이 모두 이미지 1장),
사이즈 라벨이 물리적으로 보이지 않는다. 정답이 항상 "기권"인 셋에서는 어느 쪽도 우열을 가릴 수 없다.

단서는 하나 나왔다. 무효 처리한 v2-THUMB300 실행에서 `drmartens-1461-3hole-260`에 **size 오답이 1건**
나왔다. 저해상도에서는 뭔가를 잘못 읽는다.

#### 증명된 것: 3단계 분리는 컨디션 등급에서 낫다

| | 정답 | 근사 | 오답 |
|---|---|---|---|
| v1-ORIGIN | 7 | 7 | **1** |
| v2-ORIGIN | 8 | 5 | **0** |

오답 1 → 0, 응답 정확도 47% → 62%. 전용 프롬프트 + `detail:high` + 앞 단계 맥락이 작동한다.

MODEL_NAME도 같은 방향이다. 오답 3 → 1, 정확도 67% → 80%, 대신 응답률 50% → 28%.
**덜 답하고 더 정확해졌다** — 의도한 트레이드오프지만, 사용자가 모델명을 직접 입력해야 하는 빈도는 늘어난다.

대가는 토큰 4.3배, 지연 2.9배다.

#### 증명된 것: 원본 해상도를 써야 한다

v1끼리 비교하면(`detail`은 AUTO로 동일, 해상도만 다름) 토큰을 37% 아끼는 대신
등급 정확도를 47% → 31%로 잃는다. 남는 장사가 아니다.

크롤링 데이터를 쓰는 경로에서 원본 URL(쿼리 제거)을 쓰도록 백필 쪽을 손봐야 한다.

## 2단계: 응답 스키마 고정과 근거 필수화

### 스키마를 강제로 고정한다

기존에는 `response_format: {"type": "json_object"}`만 쓰고 있었다. 이건 "JSON이기만 하면 된다"는
뜻이라, 필드가 빠지거나 이름이 달라져도 API는 정상 응답으로 취급한다. 실제로 잘못된 응답은
`objectMapper.readValue`에서 터져야 알 수 있었다.

이제 단계마다 JSON Schema를 두고 `response_format: {"type": "json_schema", "strict": true}`로 호출한다.
strict 모드에서는 OpenAI가 스키마를 강제하므로 **필드 누락이나 오타 응답 자체가 나오지 않는다.**

스키마는 프롬프트 옆에 같은 이름으로 둔다. 프롬프트와 스키마는 항상 같이 바뀌기 때문에 따로 관리하면
어긋난다.

```
prompts/vision/silhouette-v2.md      + silhouette-v2.schema.json
prompts/vision/label-v2.md           + label-v2.schema.json
prompts/vision/condition-v2.md       + condition-v2.schema.json
```

strict 모드에는 규칙이 있다. 모든 객체에 `additionalProperties: false`가 있어야 하고, `required`에
모든 속성을 적어야 하며(선택 필드는 `"type": ["string", "null"]`로 표현), `minimum` 같은 검증
키워드는 쓸 수 없다. 어기면 API가 400을 낸다 — 즉 **유료 호출을 해봐야 알 수 있다.** 그래서
`VisionResponseSchemaTest`가 이 규칙들을 파일 단위로 검사한다.

### 근거 없는 값은 코드에서 버린다

`evidence` 배열이 응답에 필수로 들어간다. 항목 하나는 이렇게 생겼다.

```json
{
  "field": "size",
  "imageIndex": 0,
  "region": "tongue_label",
  "observedText": "US 9 / 27cm",
  "observation": "텅 라벨에 사이즈가 적혀 있습니다.",
  "sourceChunkId": null
}
```

`sourceChunkId`는 지금은 항상 null이다. 나중에 `ai/search`의 청크를 프롬프트에 넣게 되면 그때
채워지는 자리로 비워뒀다. 지금 파이프라인은 이미지만 보므로 실제 근거는 `imageIndex + region +
observedText`다.

**중요한 건 이게 프롬프트 지시로 끝나지 않는다는 점이다.** "근거를 대라"고 써두면 지킬 때도 있고
아닐 때도 있다. 그래서 응답을 받은 뒤 `VisionEvidenceValidator`가 한 번 더 거른다.

- 근거가 없는 필드는 **값을 지우고** 사유를 `warnings`에 남긴 뒤 `needsUserConfirmation`을 켠다
- `size`는 근거가 있는 것만으로 부족하고, 그 근거에 **실제로 읽어낸 글자(`observedText`)가 있어야**
  한다. 사진에는 크기 기준이 없어서 눈대중 추정은 원리적으로 불가능하기 때문이다
- `imageIndex`가 실제 이미지 개수를 벗어나는 근거는 있지도 않은 사진을 가리키는 것이므로 버린다
- 등급은 근거가 없으면 `UNKNOWN`으로 되돌린다

값을 지우는 게 손해처럼 보이지만, 확인되지 않은 사이즈로 가격까지 계산되는 것보다 비워두고
사용자에게 물어보는 쪽이 낫다. 하네스의 "응답 정확도" 열이 이 판단을 검증한다.

## 3단계: 3단계 프롬프트

### 왜 호출을 나눴나

```
1단계 전체 형태  detail=low   실루엣/브랜드/모델 추정
2단계 라벨/로고  detail=high  사이즈/모델코드 판독      (1단계 결과를 맥락으로 받음)
3단계 오염/마모  detail=high  컨디션 등급 판정          (1,2단계 결과를 맥락으로 받음)
```

단계마다 필요한 게 다르다. 실루엣은 512px로 줄여도 알아볼 수 있지만 텅 라벨의 작은 글자는 원본
해상도가 필요하다. 한 호출로 묶으면 전체를 비싼 쪽에 맞춰야 한다. 나눠두면 단계별로 해상도를 따로
정할 수 있고, 뒤 단계가 앞 단계 결론을 입력으로 받아 판단을 좁힐 수 있다.

대신 이미지를 세 번 보내므로 호출 비용이 늘어난다. 그만한 값을 하는지는 하네스로 확인한다 —
`VisionPromptHarnessTest`가 v1(1회 호출)과 v2(3회 호출)를 같은 평가 셋에 돌리고, 정확도와 함께
**호출 횟수·토큰 사용량**을 같은 표에 찍는다.

단계 간 우선순위는 **라벨이 추정을 이긴다**로 정했다. 2단계가 라벨에서 읽어낸 브랜드/모델명이 있으면
그걸 쓰고, 라벨이 말해주지 않으면 1단계 추정값을 쓴다.

### 환각을 막는 방식

프롬프트에 "추측하지 마라"를 적는 것만으로는 부족해서, 세 겹으로 막는다.

| 겹 | 방법 |
|---|---|
| 스키마 | 애초에 넣을 자리를 안 준다. 1단계에는 size 필드가 없고, 어느 단계에도 희소성/연식/시세 필드가 없다 |
| 프롬프트 | 금지 대상을 구체적으로 적는다 — 희소성, 한정판 여부, 발매 연도, 생산 시기, 정품 여부, 시세. 각 단계마다 그 단계에서 빠지기 쉬운 함정을 따로 적었다 (예: 3단계의 "밑창 황변은 제품 연식의 근거가 아니다") |
| 코드 | 근거 없는 값을 버린다 (`VisionEvidenceValidator`) |

`observation`은 "무엇이 보이는지"만 쓰게 했다. `"옆면에 스우시 로고가 있습니다"`는 되고
`"나이키 제품으로 보입니다"`는 안 된다 — 후자는 관찰이 아니라 결론이라, 근거로 쓰면 순환이 된다.

### 기존 v1 구현을 남겨둔 이유

`OpenAiVisionAnalysisService`(1회 호출)는 지우지 않고 남겼다. 3단계로 나눈 게 실제로 나은지
판단하려면 같은 평가 셋에 두 구현을 돌려 비교할 수 있어야 한다.
실제 서비스가 쓰는 건 `@Primary`가 붙은 `StagedVisionAnalysisService`다.

## 4단계: detail / 해상도 결정 (측정 대기)

`detail`은 `vision.stage.*.detail` 설정으로 뺐다. 코드에 박아두면 조정할 때마다 재배포해야 하고,
비교 측정 자체가 불가능하다.

### 결론: 현행 유지 (1단계 low / 2·3단계 high)

`daangn-multi` 셋(원본 해상도, 사진 3~6장) 14건으로 두 조합을 비교했다.

| 지표 | 기본 (low/high/high) | 전부 low |
|---|---|---|
| 케이스당 토큰 | 12,036 | **5,657** (53% 절감) |
| 케이스당 지연 | 20.4초 | **14.9초** |
| BRAND 응답 정확도 | **100%** | 93% (오답 1) |
| MODEL_NAME 응답 정확도 | **88%** (오답 1) | 78% (오답 2) |
| SIZE 응답 정확도 | 50% (오답 2) | **75%** (오답 1) |
| **CONDITION_GRADE 오답** | **1건** | **1건** |

**1순위 기준인 컨디션 등급에서는 차이가 없었다.** 오답이 양쪽 1건으로 같고, 정답 수는 저화질이
6 → 7로 오히려 하나 많다. 즉 **"마모·오염 판별에 고화질이 필요한가"의 답은 '아니오'에 가깝다.**

갈린 것은 2순위인 브랜드·모델 식별이었고, 결정적인 케이스는 하나였다.

```
underarmour-curry12-225
  high → brand=Under Armour ✓  model=Curry 12 ✓
  low  → brand=Li-Ning ✗       model=Way of Wade 9 ✗
```

언더아머 커리12를 리닝 웨이드로 봤다. 둘 다 농구화라 실루엣이 비슷한데 로고를 못 읽으니 갈렸다.
**브랜드 오독은 시세 조회 키를 통째로 어긋나게 해 가격 전체가 틀어진다.**

토큰 53% 절감은 크지만, 등급 판정이 동률인 상황에서 브랜드 정확도 100% → 93%를 감수할 이유가
없다고 판단해 **현행 설정을 유지한다.**

다만 **"고화질이 압도적으로 낫다"는 결론은 아니다.** 14건 중 1건이 갈랐고 표본이 작다.
아래 두 가지가 후속 확인 대상이다.

- **1단계를 high, 2·3단계를 low로 두는 조합.** 갈린 원인이 브랜드 식별이라면 실루엣 단계를
  올리는 게 더 싸게 같은 효과를 낼 수 있다. 지금은 브랜드를 저화질로 보고 있다.
- **표본 확대.** 14건은 1건 차이로 결론이 뒤집힐 수 있는 크기다.

### 판단 기준

**size가 아니라 conditionGrade로 판정한다.** 사이즈는 사용자가 어차피 확정 입력하므로 여기서
고화질을 정당화할 근거가 못 된다. (위 "무엇을 잘해야 하는가" 참고)

| 우선순위 | 지표 | 기준 |
|---|---|---|
| 1 | `CONDITION_GRADE` **오답** 수 | 늘면 무조건 반려. 잘못 채우면 사용자가 검증 못 하고 그대로 넘긴다 |
| 2 | `BRAND` / `MODEL_NAME` 응답 정확도 | 시세 조회 키가 어긋난다 |
| 3 | 토큰 비용 | 위 둘이 같으면 싼 쪽 |
| 참고 | `SIZE` | 편의 지표. 이것만으로 고화질을 채택하지 않는다 |

즉 이 단계에서 답할 질문은 "라벨 글자가 읽히는가"가 아니라
**"마모·오염 판별에 고화질이 필요한가"** 다.

### 측정으로 정해진 것

- 원본 해상도를 쓴다 (썸네일 대비 등급 정확도 47% → 31%로 하락)
- 3단계 분리를 유지한다 (컨디션 등급 오답 1 → 0)
- `detail`은 1단계 low / 2·3단계 high를 유지한다 (위 결론 참고)

### 평가 셋이 세 개인 이유

셋마다 잴 수 있는 게 다르다.

| 셋 | 이미지 | 해상도 | 쓰임 |
|---|---|---|---|
| `daangn` | 1장 | 원본 | 최초 기준선 (측정 완료) |
| `fruitsfamily` | 6장 | 620px 고정 | 다중 이미지 효과 (측정 완료) |
| `daangn-multi` | 3~6장 | 원본 | **`detail` low/high 비교의 유일한 근거** |

`daangn-multi`는 당근 이미지 파일명이 `{해시}_0.webp` 형태라는 걸 이용해 만들었다. `_1`, `_2`...를
404가 날 때까지 HEAD로 찔러보면 상세 페이지를 열지 않고도 같은 매물의 나머지 사진을 알아낼 수 있다.
(당근 3,337건 중 이 파일명 체계는 1,352건이고, 나머지는 다른 체계라 이 방법이 안 통한다)

### 분당 토큰 한도

조직 TPM이 30,000인데 이미지 6장짜리 케이스는 약 14,000 토큰을 쓴다. 쉬지 않고 돌리면 분당 2건에서
한도에 닿는다.

`OpenAiVisionClient`가 429를 재시도하는데, 처음에는 고정 백오프(1/2/4초)만 써서 창이 안 풀린 채 다시
찌르다 재시도 횟수만 태우고 실패했다. 지금은 `retry-after-ms` 헤더나 응답 본문의
"try again in 5.768s"를 읽어 그만큼 기다린다.

그래도 평가 셋을 키우면 측정 시간이 한도에 묶인다는 점은 남는다. 17건 측정에 7분이 걸렸고 대부분이
대기 시간이었다.

## JSON 준수율 실측 (2026-09-02)

Week 7 항목 "브랜드 인식률, 상태 인식률, JSON 준수율 측정" 중 마지막으로 비어 있던
숫자다. 집계 기능은 #51에서 만들었지만(API 오류를 분모에서 제외, 예외 타입으로 분류)
실제로 돌려서 기록한 적이 없었다.

실행: `daangn` 셋 18건, V2(3단계), 원본 해상도, detail 기본(low/high/high).
API 54회, 토큰 105,497(케이스당 5,860), 케이스당 평균 12.6초.

### 결과: 100% (응답 18건 중 형식 오류 0건)

Structured Outputs(`json_schema` + `strict`)를 쓰는 한 예상된 값이다. 그래서 이 측정의
의미는 "문제없음을 확인했다"가 아니라 **회귀 기준선을 만들었다**는 데 있다 - 이 값이
100% 아래로 내려가면 응답이 잘리고 있거나(max_output_tokens 부족) 스키마 자체가
깨진 것이므로, 프롬프트·스키마를 바꿀 때마다 이 숫자를 같이 봐야 한다.

### 같이 나온 필드별 수치 (참고)

| 필드 | 응답률 | 응답 정확도 | 비고 |

| MODEL_NAME | 22% | 100% | 모르면 기권한다 - 낮은 응답률은 의도된 보수성 |

## 색상(color) 정확도 실측 (2026-09-04, #90)

color는 사용자 확인 화면에 노출되고 2순위 가격 매칭 조건에도 들어가는데 채점된 적이
없었다. 채점 기준을 정의하고 기준선을 만들었다.

### 채점 기준

- **정답**: 판매자 표기와 단어 단위로 겹침 ("울프그레이" 정답에 "Wolf Grey")
- **근사**: 표기는 달라도 색 계열이 겹침 (Cream ↔ Beige). 계열 매핑은
  `ColorFamilies.java`에 판단 근거와 함께 고정 - 프롬프트가 공식 컬러웨이명을
  금지하므로 같은 계열의 다른 표기를 오답으로 갈라서는 안 된다
- 정답 라벨은 판매글 제목에 색상이 명시된 25건만 라벨링했다(전체 49건).
  제목에 색이 없는 케이스는 채점 제외 - 없는 정답을 지어내지 않는다

### 결과: 응답한 19건 중 정답 15, 오답 4 (정확 79%, 계열 근사 0건)

실행: 3개 셋 전체, V2, 원본 해상도. fruitsfamily 셋 도중 OpenAI 크레딧 소진으로
라벨 6건이 미측정으로 남았다(충전 후 재실행 예정 - 아래 수치는 응답분 기준).

| 셋 | 채점(응답) | 정답 | 오답 |
| --- | --- | --- | --- |
| daangn | 9 | 6 | 3 |
| daangn-multi | 7 | 6* | 1 |
| fruitsfamily | 3 | 3 | 0 |

\* 체커보드 케이스는 첫 라벨(흑백 가정)이 오류였다. 판매자는 패턴만 명시했는데
모델이 "red and blue checkered"로 답해 드러남 - 라벨을 패턴 단어로 수정하고
재채점한 값이다. 계열 테이블에서도 패턴을 제거했다(색이 아니므로).

### 실패 패턴: 전부 저채도·어두운 색 경계

오답 4건 모두 색 계열 자체를 놓친 경우다: 민트→light blue, 회색→black,
브라운→black and white, 베가스 골드→beige and orange. 채도가 낮거나 어두운
색이 조명에 따라 이웃 계열로 읽히는 문제로, 환각(없는 색을 지어냄)과는 성격이
다르다. 근사(계열 일치) 판정이 0건인 것도 특징 - 맞을 때는 표기까지 맞고,
틀릴 때는 계열째 틀린다.

### 회귀 기준선으로서의 사용법

프롬프트·detail 옵션을 바꿀 때 이 표를 다시 뽑아 비교한다. 정확도가 떨어지거나,
지금 0건인 "계열 근사"가 늘어나면(표기가 흐려짐) 색상 판정이 나빠진 것이다.
