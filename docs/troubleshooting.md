# 트러블슈팅 기록

AI·조회 트랙에서 실제로 막혔던 문제와 해결 과정을 남긴다.

정리하다 보니 절반 이상이 같은 성격이었다. **에러가 나지 않아서 한동안 몰랐던 문제들**이다.
예외가 터지는 버그는 스택트레이스가 위치를 알려주지만, 아래 사례들은 로그가 깨끗하고
테스트가 초록불인 채로 잘못된 값을 만들어내거나 아무 일도 하지 않고 있었다.
그래서 "무엇이 이 실패를 조용하게 만들었는가"를 각 항목에 같이 적었다.

| # | 문제 | 조용했던 이유 |
| --- | --- | --- |
| 1 | 상품 벡터가 한 번도 저장되지 않음 | 컬럼 타입을 JPA가 알아서 정해줬다 |
| 2 | 예외를 잡았는데 호출부가 롤백됨 | 실패 시점이 `catch` 블록 바깥이었다 |
| 3 | 추천 응답시간이 경매 수에 정비례 | 개발 데이터가 4건뿐이었다 |
| 4 | KREAM 수집이 18분간 0건 | 차단을 403이 아니라 500으로 알려줬다 |
| 5 | 조던 시세가 통째로 안 잡힘 | 두 소스의 브랜드 표기가 달랐다 |
| 6 | 평가 하네스가 매번 통과 | 실행 자체가 skip되고 있었다 |
| 7 | 테스트 14건이 한꺼번에 실패 | 프로덕션 변경을 테스트가 못 따라갔다 |

7번을 뺀 나머지는 전부 "실패했다는 신호가 없었다"는 공통점이 있다.

## 1. 1536차원 벡터가 한 번도 저장되지 않았다

**증상**

추천 기능(#49)을 만들고 로컬에서 상품을 등록했더니 HTTP 500이 났다.
단위 테스트는 전부 통과한 상태였다.

**진단**

로그를 보니 상품 저장이 아니라 벡터 저장에서 났다.

```
Data too long for column 'vector_bytes'
```

생성된 테이블을 확인했다.

```sql
SHOW COLUMNS FROM product_vectors;
-- vector_bytes  tinyblob
```

`TINYBLOB`은 255바이트다. `text-embedding-3-small`은 1536차원이고 float 하나가 4바이트라
**6,144바이트**가 필요하다. 24배 넘게 모자랐다.

**원인**

엔티티에 `@Lob`만 붙였다.

```java
@Lob
@Column(name = "vector_bytes", nullable = false)
private byte[] vectorBytes;
```

`@Lob`은 "큰 객체"라는 뜻이지 크기를 지정하지 않는다. Hibernate가 MySQL 방언에서
기본 타입을 고르는데 그게 `TINYBLOB`이었다.

**해결**

컬럼 타입을 직접 명시했다.

```java
@Lob
@Column(name = "vector_bytes", nullable = false, columnDefinition = "LONGBLOB")
private byte[] vectorBytes;
```

**배운 것**

단위 테스트가 이걸 못 잡은 이유가 핵심이다. 리포지토리를 목으로 대체했기 때문에
**DDL이 만들어지는 경로 자체를 지나지 않았다.** 스키마는 실제 DB에 붙여봐야 검증된다.

`@Lob`처럼 프레임워크가 세부를 알아서 정해주는 애너테이션은, 그 "알아서"가 무엇으로
결정됐는지 한 번은 확인해야 한다. 여기서는 `SHOW COLUMNS` 한 줄이면 됐다.

## 2. 예외를 잡았는데도 호출부가 롤백됐다 (같은 패턴을 두 번 만났다)

이 문제는 두 번 나왔고, 두 번째에 더 깊은 원인을 찾았다.

### 2-1. 첫 번째 — 상품 등록이 벡터 때문에 실패했다 (#49)

**증상**

1번을 고치기 전, 벡터 저장이 실패하면 **상품 등록 전체가 HTTP 500**으로 실패했다.
추천은 부가 기능이라 실패해도 상품은 등록돼야 하는데 그렇지 않았다.

**진단**

코드에는 분명히 예외를 잡고 있었다.

```java
try {
    return productVectorRepository.save(ProductVector.of(...));
} catch (RuntimeException e) {
    log.warn("상품 벡터 생성에 실패했습니다. ...");
    return null;   // 여기로 오지 않았다
}
```

로그에 `상품 벡터 생성에 실패했습니다`가 **찍히지 않았다.** 예외가 이 `try` 안에서
나지 않았다는 뜻이다.

**원인**

두 가지가 겹쳐 있었다.

첫째, `save()`는 영속성 컨텍스트에 등록만 하고 **INSERT를 즉시 실행하지 않는다.**
실제 INSERT는 트랜잭션이 커밋될 때, 즉 이 메서드가 반환된 **뒤에** 나간다.
그래서 `catch`를 그냥 지나쳤다.

둘째, 상품 등록과 벡터 생성이 **같은 트랜잭션**이었다. 커밋 시점에 터진 예외가
트랜잭션을 `rollback-only`로 표시했고, 상품 등록까지 함께 무효가 됐다.

**해결**

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public ProductVector refresh(Product product) {
    try {
        // saveAndFlush로 INSERT를 이 자리에서 실행해 실패를 catch 안에서 잡는다
        return productVectorRepository.saveAndFlush(ProductVector.of(...));
    } catch (RuntimeException e) {
        log.warn(...);
        return null;
    }
}
```

`REQUIRES_NEW`로 트랜잭션을 분리하고, `saveAndFlush`로 실패 시점을 `try` 안으로 당겼다.

### 2-2. 두 번째 — AI 호출 로그에서 다시 만났다 (#51)

**증상**

AI 호출 기록을 만들면서 같은 원칙을 적용했다. "기록 실패가 AI 분석을 실패시키면 안 된다."
2-1에서 배운 대로 `REQUIRES_NEW` + `saveAndFlush` + `catch (Throwable)`까지 썼다.

그리고 이걸 검증하는 테스트를 짰는데 **실패했다.**

```
Expecting code not to raise a throwable but caught
  "java.lang.RuntimeException: 기록 저장 실패
```

**원인**

`@Transactional`은 프록시로 동작한다. 프록시가 메서드를 감싸고, **커밋은 메서드가
반환된 다음에** 프록시가 실행한다.

```
[프록시]  트랜잭션 시작
            [내 메서드]  try { saveAndFlush } catch { ... }   <- 여기까지가 내 코드
          커밋                                                  <- 예외가 여기서 나면?
```

즉 `saveAndFlush`로 대부분의 실패는 `try` 안으로 당겨왔지만, **커밋 자체가 실패하는 경우는
여전히 내 `catch` 바깥**이었다. 2-1에서 고친 건 증상이었고 구조는 그대로였던 것이다.

**해결**

쓰기를 별도 빈으로 분리해서 **프록시 경계를 내 `try` 안쪽으로 옮겼다.**

```java
@Component
class AiCallLogWriter {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void write(AiCallLog log) {       // 프록시 경계가 여기
        repository.saveAndFlush(log);
    }
}

@Service
class AiCallLogger {
    public void record(AiCallLog log) {
        try {
            writer.write(log);               // 커밋 실패도 이 호출에서 튀어나온다
        } catch (Throwable e) {
            log.warn(...);                   // 이제 정말로 다 잡힌다
        }
    }
}
```

**배운 것**

`@Transactional`을 붙인 메서드 **안에서** 그 트랜잭션의 실패를 잡을 수는 없다.
프록시 경계 밖에서 잡아야 하고, 그러려면 클래스를 나눠야 한다.

그리고 이 문제는 **테스트를 먼저 짰기 때문에** 발견됐다. "예외를 절대 안 던진다"는
주석을 달아놓고 실제로는 보장하지 못하는 코드였는데, 그걸 검증하는 테스트가 없었다면
운영에서 AI 분석이 통째로 실패하고 나서야 알았을 것이다.

## 3. 병목은 유사도 계산이 아니라 데이터 전송이었다

**증상**

추천 API를 만들고 나서 "요청마다 벡터를 DB에서 읽는 방식이 느리지 않을까" 하는 의심이 있었다.
개발 데이터가 상품 4건뿐이라 체감이 없었다.

**측정**

임베딩을 진짜로 만들면 비용이 드니까, **난수 벡터를 DB에 직접 넣어** 규모를 키웠다.
코사인 유사도 계산 비용은 벡터 값과 무관하므로 이래도 결과는 같다.

비교 기준이 문제였다. 이슈에는 "기존 목록 조회 대비"라고 적었는데 `GET /api/auctions`가
아직 없었다. 대신 **같은 엔드포인트의 Cold Start Fallback 경로**를 기준으로 삼았다.
Fallback은 벡터를 전혀 쓰지 않는 순수 DB 쿼리라, 두 경로의 차이가 곧 추천 엔진이
추가한 비용이 된다.

각 50회, p50 기준:

| 경매 수 | Fallback | 개인화 | 추가 비용 |
| --- | --- | --- | --- |
| 100 | 33ms | 46ms | +13ms |
| 1,000 | 33ms | 131ms | +98ms |
| 3,000 | 29ms | 317ms | +288ms |

Fallback은 `LIMIT` 쿼리라 경매 수와 무관하게 평평했고, 개인화만 정비례로 늘었다.

**원인**

처음에는 3,000 × 1,536차원 코사인 계산이 병목일 거라고 생각했다. 따로 재보니 아니었다.

벡터 하나가 6KB다. 3,000건이면 요청마다 **17.6MB**를 DB에서 읽어온다.
유사도 계산 자체는 JVM에서 수 ms다. **병목은 계산이 아니라 전송이었다.**

**결정**

고치지 않고 한계를 기록했다. 데모 규모(경매 수백 건)에서는 +13ms라 영향이 없고,
캐싱은 "경매 목록 API + Redis 캐싱" 작업에서 함께 다루는 게 자연스럽다고 봤다.

대신 코드에 숫자를 남겼다.

```java
// 로컬 측정(경매 1건당 벡터 6KB, Fallback 경로 대비 추가 시간):
//   경매 100건 -> +13ms / 1,000건 -> +98ms / 3,000건 -> +288ms
// 대부분이 유사도 계산이 아니라 BLOB 전송 비용이다(3,000건 = 17.6MB).
```

**배운 것**

이슈에는 원래 "벡터를 기동 시 메모리에 로드"라고 적었는데, 구현할 때 "메모리를 아끼고
갱신이 즉시 반영된다"는 이유로 요청마다 읽는 방식으로 바꿨다.
**측정해보니 원래 설계가 이 지점에서는 옳았다.**

설계를 바꿀 때 이유가 그럴듯하면 검증을 건너뛰기 쉽다. 그리고 개발 데이터가 4건이면
어떤 성능 문제도 보이지 않는다. 규모를 인위적으로 키워서 재봐야 한다.

## 4. 차단을 403이 아니라 "10초 걸리는 500"으로 알려줬다

**증상**

KREAM 시세 수집을 재실행했는데 **18분 동안 0건**이었다. 크래시도 없고 로그도 계속 돌았다.

**진단**

20분 전에 정상 수집됐던 페이지를 다시 요청해봤다. 그것도 500이 왔다.
**데이터 문제가 아니라 클라이언트가 차단된 상태**였다.

특이한 건 응답 형태였다. 보통 차단은 403이나 429로 오는데, KREAM은 **응답에 10초를 쓰고
500을 반환**했다. 코드 입장에서는 "서버가 잠깐 불안정한" 것과 구분되지 않는다.

**원인**

재시도 로직이 500을 일시적 오류로 보고 계속 재시도했다. 한 요청에 10초씩 쓰면서
차단된 상태로 몇 시간을 돌 수 있는 구조였다.

**해결**

세 가지를 넣었다.

- **서킷 브레이커**: 연속 5회 실패하면 소프트 차단으로 판단하고 전체 중단
- **페이스 조정**: 요청 간격을 10~20초로 늘리고, 차단 감지 시 120초 쿨다운
- **배치 저장 순서 변경**: 중단 전에 모은 것을 먼저 저장 — 이전에는 차단되면 그때까지
  수집한 배치가 통째로 날아갔다

**배운 것**

외부 API의 실패 응답을 액면 그대로 믿으면 안 된다. **500이 항상 "일시적"을 뜻하지는 않는다.**

그리고 "재시도"는 그 자체로 위험할 수 있다. 상대가 차단 의도로 응답을 늦추고 있을 때
재시도는 상황을 악화시킨다. 재시도에는 **포기 조건**이 반드시 있어야 한다.

## 5. 브랜드 표기가 달라서 조던 시세가 통째로 안 잡혔다

**증상**

가격 추천이 조던 계열 상품에서 유독 근거 데이터가 적었다.

**진단**

두 시세 소스의 데이터를 나란히 놓고 봤다.

| 소스 | brand | model |
| --- | --- | --- |
| eBay | `Nike` | `Air Jordan 1 ...` |
| KREAM | `Jordan` | `Jordan 1 ...` |

사용자가 브랜드를 `Nike`로 입력하면 **KREAM의 조던 시세가 하나도 매칭되지 않았다.**
조회 자체는 정상 동작하고 결과가 0건일 뿐이라 에러가 나지 않았다.

**해결**

KREAM CSV 15행을 `brand=Nike`로 바꾸고 모델명을 `Air Jordan ...` 형태로 맞췄다.
Vision 평가 셋에서도 `Jordan`을 정답 후보에서 제외했다 — **시세 조회 키는 하나여야 한다.**

**배운 것**

두 데이터 소스를 합칠 때 스키마가 같다고 값의 표기까지 같지는 않다.
`brand`라는 컬럼이 양쪽에 있다는 것과, 같은 신발에 같은 값이 들어 있다는 것은 다른 얘기다.

이런 종류의 불일치는 **조회 결과가 0건일 뿐 에러가 아니라서** 발견이 늦는다.
소스를 추가할 때 조인 키가 될 컬럼은 값 분포를 직접 확인해야 한다.

## 6. 평가 하네스가 실행되지 않고 통과하고 있었다

**증상**

Vision 프롬프트 평가 하네스를 만들고 실행했는데 몇 초 만에 `BUILD SUCCESSFUL`이 떴다.
실제 API를 호출하면 케이스당 수십 초가 걸려야 정상이다.

**원인 (세 겹이었다)**

첫째, **Gradle의 `-D` 옵션은 Gradle JVM에만 설정된다.** 테스트는 별도 JVM에서 돌기 때문에
`-Dvision.harness=true`가 테스트에 전달되지 않았고, 하네스는 조건을 만족하지 못해
조용히 skip됐다.

둘째, 이를 고친 뒤에는 **두 번째 실행부터 `UP-TO-DATE`로 건너뛰었다.** 하네스는 매번
실제 API를 호출해 새 수치를 내는 게 목적이라 캐싱되면 안 된다.

셋째, 실행이 되고 나서도 결과가 안 보였다. **Gradle은 테스트의 `System.out`을 기본으로 숨긴다.**
하네스는 출력이 곧 결과물이라 수 분을 기다린 끝에 `BUILD SUCCESSFUL`만 보게 됐다.

**해결**

```groovy
tasks.named('test') {
    def harnessProperties = System.properties.findAll { it.key.toString().startsWith('vision.harness') }
    harnessProperties.each { key, value -> systemProperty(key.toString(), value.toString()) }

    if (!harnessProperties.isEmpty()) {
        outputs.upToDateWhen { false }              // 매번 새로 돌아야 한다
        testLogging { showStandardStreams = true }  // 출력이 곧 결과물이다
    }
}
```

덧붙여 PowerShell에서는 `-Dvision.harness=true`가 `-Dvision`과 `.harness=true`로 쪼개져
전달됐다. 각 `-D` 인자를 따옴표로 감싸야 했다.

**배운 것**

**"통과했다"와 "실행됐다"는 다르다.** skip된 테스트는 초록불로 표시되고, 조건부로 도는
테스트일수록 이 함정에 빠지기 쉽다.

측정을 위한 코드는 결과가 눈에 보이는지까지 확인해야 한다. 실행은 되는데 출력이 숨겨져
있으면 실행 안 된 것과 구분되지 않는다.

## 7. 테스트가 프로덕션 변경을 따라가지 못해 14건이 한꺼번에 깨졌다

**증상**

추천용 행동 로그를 남기려고 `AuctionController`에 `ActivityLogService` 의존성을 추가했더니
`AuctionControllerTest` 14건이 한꺼번에 실패했다.

**원인**

`@WebMvcTest`는 컨트롤러가 필요로 하는 빈을 모두 목으로 제공해야 컨텍스트가 뜬다.
새 의존성에 `@MockitoBean`이 없어서 **컨텍스트 로딩 단계에서 전부 깨졌다.**
테스트 내용이 틀린 게 아니라 시작조차 못 한 것이다.

같은 원인으로 `MockAuthInterceptorTest` 5건도 깨져 있었는데, 이건 **내 작업 전부터
`main`에서 깨져 있던 것**이었다. 확인해보니 컨트롤러가 `BidCommandService`에서
`ManualBidService`로 바뀌고 `Idempotency-Key`가 필수 헤더가 되는 동안 테스트가
따라가지 않은 상태였다.

**해결**

- `AuctionControllerTest`에 `@MockitoBean ActivityLogService` 추가
- `MockAuthInterceptorTest`의 목을 현재 의존성에 맞추고 필수 헤더 추가

**배운 것**

슬라이스 테스트는 프로덕션 구조와 강하게 결합돼 있다. 컨트롤러에 의존성 하나만 추가해도
관련 테스트가 전부 멈춘다. 이건 설계상 어쩔 수 없는 비용이다.

다만 **깨진 테스트를 방치하면 그 뒤로는 아무것도 알려주지 않는다.** `MockAuthInterceptorTest`
5건이 계속 빨간불이었는데, 이 상태에서는 새로 깨진 게 생겨도 묻힌다.
내 작업 범위가 아니어도 고치고 가는 게 맞다고 판단했다.

## 정리하며

7건 중 5건이 "에러 없이 잘못 동작하던" 문제였다. 공통점을 정리하면 이렇다.

**프레임워크가 알아서 정해준 것을 확인하지 않았다** (1번 `@Lob`, 2번 `@Transactional` 프록시).
편의를 위한 추상화는 세부를 감추는데, 그 세부가 틀리면 증상은 엉뚱한 곳에서 나타난다.

**개발 환경의 규모가 문제를 가렸다** (3번). 데이터 4건에서는 어떤 성능 문제도 보이지 않는다.

**정상 응답과 실패가 형태로 구분되지 않았다** (4번 500, 5번 0건 조회).
둘 다 "에러가 아닌 실패"라 예외 처리로는 잡을 수 없고, 값을 직접 봐야 발견된다.

**실행되지 않은 것과 통과한 것이 같아 보였다** (6번).

그래서 얻은 습관은 하나다. **중요한 경로는 실제로 돌려보고 결과를 눈으로 확인한다.**
1번과 2번은 로컬에 DB를 띄워 상품을 등록해봐서 찾았고, 3번은 규모를 인위적으로 키워서
쟀고, 5번은 두 CSV를 나란히 놓고 봐서 알았다. 단위 테스트만으로는 하나도 못 잡았을 것이다.
