## Day 13 성능 결과의 역할
Day 13은 **같은 PoC 안의** 동기 vs 비동기, API 1대 vs 2대, 요청량 vs 큐 대기를 비교한다.
Redis Streams와 SQS의 성능 비교가 아니므로 **큐 선택의 판정 기준으로 쓰지 않는다.**
용량 계획(Worker 수, 병목 지점)의 근거로만 사용한다.

presign·PUT은 k6 기본 timeout(60초)
결과 문서에는 Visibility Timeout 실제 값 120초

실험 1: 동기 vs 비동기 예측

조건	HTTP 응답	E2E	이유
sync, 동시성 2	약 11.2초	약 11.2초	HTTP 요청이 처리 끝까지 대기
sync, 동시성 10	약 11.2초	약 11.2초	API 스레드 200개라 10개 동시 처리 가능

async, 동시성 10	수십 ms	평균 약 60초, p95 약 110초	Worker 2대가 2건씩만 처리, 나머지는 큐 대기

실험 2: API 1대 vs 2대 (약 55분)

부하	예측	이유
VU 10	1대와 2대가 비슷	서버가 포화되지 않아 응답시간 위주
VU 50·100	2대가 처리량 더 높음, 단 2배 미만	경매 조회는 캐시 없이 매번 DB 조회. API CPU가 포화되면 2대가 유리하지만, DB나 Load EC2가 먼저 포화되면 그만큼 덜 늘어남

-> 문서 원칙대로 2배가 안 나와도 되고, 포화된 지표로 병목을 하나 이상 지목하는 게 목표


실험 3: 분석 요청 증가 vs Queue
Worker 2대가 11.16초마다 2건씩 처리합니다. N건이 한꺼번에 들어오면:

drain time      ≈ (N ÷ 2) × 11.16초
queueWait 최대  ≈ (N ÷ 2 − 1) × 11.16초
E2E 평균        ≈ 11.16 × (N ÷ 2 + 1) ÷ 2초

N	drain	queueWait 최대	E2E 평균
10	약 56초	약 45초	약 33초
50	약 279초	약 268초	약 145초
100	약 558초	약 547초	약 290초

실측은 여기에 큐 전달과 polling 간격(1초)만큼 1~2초 더해질 것으로 예측
